Design invariants

  • Preserve raw data; do not redact in v1.
  • Bundles are immutable and SHA-256 addressed.
  • Corpus is derived and rebuildable from depot bundles.
  • SQLite + FTS5 is the search engine; no custom index.
  • Search snippets are leads; agents read refs before answering.
  • Public JSON / refs / docs are tested contracts.

The cleverest, most novel parts novel

Most of aha is plumbing. These are the load-bearing ideas worth slowing down for.

1. Session-key construction novel

Why it's clever: session identity must be stable across machines, across multiple captures of the same session, and across slight changes in the raw file (e.g. an in-progress JSONL grows). The session key is sk1_ + sha256 of a length-prefixed tuple (source, machine, source_session_id). Length-prefixing prevents the classic concatenation-collision where ("pi", "abc") and ("pia", "bc") would hash identically. Two tables in the DB pin the relationship; a trigger refuses any other shape.

// internal/model/identity.go
func NewSessionKey(source, machine, sourceSession string) (SessionKey, error) {
    h := sha256.New()
    writeLengthPrefixed(h, source)         // 8 BE bytes of len, then bytes
    writeLengthPrefixed(h, machine)
    writeLengthPrefixed(h, sourceSession)
    return SessionKey{value: "sk1_" + hex.EncodeToString(h.Sum(nil))}, nil
}
-- internal/corpus/schema.go (sessions table)
session_key text primary key
  check(length(session_key)=68
        and substr(session_key,1,4)='sk1_'
        and substr(session_key,5) not glob '*[^0-9a-f]*'),

-- and a trigger that aborts any other shape:
create trigger sessions_require_v2_key before insert on sessions
  when new.session_key='' or length(new.session_key)<>68
       or substr(new.session_key,1,4)<>'sk1_'
       or substr(new.session_key,5) glob '*[^0-9a-f]*'
  begin select raise(abort,'session key must be sk1'); end;

2. Sealed canonical refs novel

Why it's clever: the boundary between humans/agents and the corpus is exactly one type, model.Ref, with three sealed variants. Refs round-trip: every search hit emits a ref_text, every read <ref> parses it back. The refVariant() method is unexported so no outside package can implement Ref — closed sum type in Go.
message ref →
session ref →
artifact ref →
parse(msg) → kind
Try pasting msg:v1:<b64>:<b64> into the entry input; everything below updates live.
The closed sum type, in code 
// internal/model/ref.go
type Ref interface {
    refVariant()          // unexported → no outside impls
    Kind() RefKind
    Valid() bool
}
type MessageRef  struct { Session SessionKey; Entry EntryID }
type SessionRef  struct { Session SessionKey }
type ArtifactRef struct { SHA SHA256Hex }

func FormatRef(r Ref) string {
    switch r := r.(type) {
    case MessageRef:  return "msg:v1:"     + b64(r.Session.String()) + ":" + b64(r.Entry.String())
    case SessionRef:  return "session:v1:" + b64(r.Session.String())
    case ArtifactRef: return "artifact:v1:" + r.SHA.String()
    }
    panic("unknown ref variant")
}

3. Manifest state signature — refresh idempotency novel

Why it's clever: refresh needs to know "is the source state the same as the last bundle I made?" but the literal bundle SHA changes every time because bundle_id and captured_at are unique per capture. The fix is a second SHA that excludes volatile fields:
Why this is more interesting than it looks
  • It enables zero-fetch refresh: if the catalog already has a ref with the same state hash, we don't even download the old bundle to confirm — metadata alone proves equivalence.
  • It's enforced by a property test: any change to volatile metadata must not change ManifestStateSHA256; any change to content must.
  • It's a deliberate departure from "one SHA to rule them all." The bundle SHA proves byte identity; the state SHA proves source-state equivalence.

4. Append-only corpus + conflict-as-quarantine novel

Why it's clever: two snapshots of the same Pi session can disagree on a previously-written line (active JSONL files, edits, replays). A naïve UPSERT loses evidence. The schema makes that impossible: append-only triggers abort any update or delete on entries, messages, artifacts, and conflicts. A conflict trigger quietly inserts a conflict row when a duplicate entry_id arrives with a different entry_sha256, then RAISE(IGNORE) swallows the new row. 
create trigger entries_conflict_before_insert
  before insert on entries
  when exists(select 1 from entries
              where session_key=new.session_key and entry_id=new.entry_id) begin
    insert into conflicts(session_key, entry_id, first_entry_sha256, second_entry_sha256, details_json)
      select new.session_key, new.entry_id, e.entry_sha256, new.entry_sha256,
             json_object('kind','same-session-trigger')
        from entries e
       where e.session_key=new.session_key and e.entry_id=new.entry_id
         and e.entry_sha256<>new.entry_sha256;
    select raise(ignore);   -- drop the new row, keep the original
  end;

create trigger entries_no_update before update on entries
  begin select raise(abort,'entries are append-only'); end;
What this rules out
  • A second ingest can never silently overwrite an entry that disagrees.
  • The conflict itself is append-only — you can read the disagreement later via aha conflicts.
  • The static debt inventory (internal/testquality) fails CI if any production code tries to UPDATE or DELETE these tables directly.

5. Trigger-maintained FTS + repairable derivation novel

Why it's clever: the FTS5 virtual tables are derived, but they're maintained synchronously by triggers on the source tables — so normal writes can't drift. Verification compares rowid identity (cheap query plan), and a public aha verify --repair-fts exists for the fallback case. This is a real "make illegal states unrepresentable, then handle the residual." pattern. 
-- on every message insert, mirror text into FTS:
create trigger messages_ai after insert on messages
  when trim(coalesce(new.text,''))<>'' begin
    insert into fts_messages(rowid,session_key,entry_id,text)
      values(new.rowid, new.session_key, new.entry_id, new.text);
  end;

-- ftsMessageTextPredicate("")  ==  trim(coalesce(text,''))<>''
-- the SAME expression is reused in:
--   * the schema trigger above
--   * corpus.Verify       (which messages SHOULD have FTS rows?)
--   * ReconcileFTS        (which rows to re-insert)
-- so verify and repair can never disagree on what counts as indexable.
The cleanup that made this honest

Until migration v7 the artifact trigger used a slightly different predicate than the verifier — so verify would flag missing FTS rows that --repair-fts wouldn't repair. The duplication-refactor pass moved both to a shared ftsArtifactTextPredicate and added a migration that recreates the trigger on existing corpora.

6. Known-SHA handoff — writing the bundle and trusting it once novel

Why it's clever: a naïve pipeline computes the bundle SHA three times: once when writing, once when publishing to the depot, once when ingesting. archive.WriteWithInfo threads a single WriteInfo{BundleSHA256, SizeBytes, ManifestSHA256, StateSHA256} down to depot.PutBundleKnown and corpus.IngestBundleWithExpectedSHA. The integrity boundary stays at staging (where untrusted bytes first land), but redundant rehashes go away. 
// archive.Write computes compressed SHA while writing.
info, _ := archive.WriteWithInfo(manifest, files, path)

// depot trusts that identity instead of re-reading the finished bundle:
ref, created, _ := depot.PutBundleKnown(ctx, driver, path,
    depot.BundleRefFromWriteInfo(manifest, info, filepath.Base(path)))

// ingest verifies an expected SHA on the staged copy, not after the fact:
rep, _ := corpus.IngestBundleWithExpectedSHA(store, registry, bundlePath, info.BundleSHA256)

7. Search = two FTS queries merged in Go + defensive escaping novel

Why it's clever: messages and artifacts live in two separate FTS5 tables (fts_messages, fts_artifacts). A single search runs both with the same filters, each capped at the limit, then merges and re-sorts in Go by bm25 score (lower is more relevant), with deterministic tiebreakers down to entry_id. The result is capped once more. So ranking is stable and reproducible — a tested contract, not whatever order SQLite happened to return.

The other half is ftsQuery: arbitrary human text is never handed to FTS5 raw. Each whitespace term is quoted (and embedded quotes doubled), which neutralizes FTS operators like AND, NEAR, *, and column filters. Type anything below and watch what actually reaches SQLite.

Ingest: the most fiddly state machine novel

Ingest is the only path that takes untrusted bytes and writes into the live corpus. It splits cleanly into three roles — planner → writer → publisher — and the order of commit vs publish is load-bearing.

Read-visibility invariant

A reader from another connection must not see uncommitted ingest rows. There's a paired property test: a goroutine holds the writer at afterManifestFiles, a separate reader calls search.Query and corpus.ReadContext; both see zero rows until commit, then full rows after. This is the contract that makes "search → read" coherent for agents.

Three-layer deduplication novel

Three different keys, three different blast radii. Each layer dedups a different kind of duplication — and they compose.
