Gotchas

Five things that look like they should work but don't, and what to do instead. The architecture is opinionated; these are the load-bearing opinions made visible.

If you try…What happensDo this instead
DELETE FROM entries WHERE … Trigger entries_no_delete aborts with "entries are append-only". The transaction rolls back. A static test in internal/testquality also blocks this from production code at CI time. If the row is wrong, aha verify --repair-fts rebuilds derived FTS; corpus identity stays. To genuinely remove evidence, drop the corpus and re-ingest from depot bundles selectively.
UPDATE entries SET role=… Same: entries_no_update aborts. Entries, messages, artifacts, and conflicts are all append-only. If two snapshots disagree, the second goes into conflicts automatically. Inspect with aha conflicts.
Pass --depot to aha search or aha read Search and read are corpus-only operations. The flag isn't accepted; you get a parse error. If you need a different corpus, use --repo DIR. If you need a different depot, run aha refresh --depot … first, then search the corpus that ingest produced.
Query fts_messages MATCH ? with raw user text FTS5 interprets characters like AND, NEAR, *, : as operators. A user search for title:secret would silently become a column filter. Always pass user text through search.ftsQuery() first; it quotes each whitespace-separated term and doubles embedded ". The FTS escaping playground above shows the rule.
Hard-code R2 credentials in config.jsonc Config schema doesn't accept secret fields. A round-trip test asserts secrets never appear in serialized output. Set AHA_R2_ACCESS_KEY_ID / AHA_R2_SECRET_ACCESS_KEY (or the unprefixed R2_* variants) in the environment. The depot driver reads them at startup; they live only in process memory.
Compute identity by string-concatenating tuples Two distinct tuples can hash identically: ("pi","abc") and ("pia","bc") collide. The static test in internal/testquality rejects raw +/strings.Builder over identity inputs. Use model.NewSessionKey(source, machine, source_session_id). It length-prefixes each segment before hashing. The session-key playground above demonstrates the collision-prevention property.

Mechanisms

Eight places in the codebase where a type, a SQL constraint, or a small algorithm replaces what would otherwise be a comment and a runtime check. Most of the rest of aha is plumbing around these.

Session-key construction

internal/model/identity.go

Session identity must be stable across machines, across captures of the same session, and across slight changes in the raw file (an in-progress JSONL grows). The session key is sk1_ + sha256 of a length-prefixed tuple (source, machine, source_session_id). Length-prefixing kills the classic concat collision where ("pi", "abc") and ("pia", "bc") would hash identically. The DB enforces the shape with a CHECK and a trigger that aborts any non-sk1_ insert.

Where this lives 
// internal/model/identity.go
func NewSessionKey(source, machine, sourceSession string) (SessionKey, error) {
    h := sha256.New()
    writeLengthPrefixed(h, source)         // 8 BE bytes of len, then bytes
    writeLengthPrefixed(h, machine)
    writeLengthPrefixed(h, sourceSession)
    return SessionKey{value: "sk1_" + hex.EncodeToString(h.Sum(nil))}, nil
}

The boundary between humans, agents, and the corpus is a single type model.Ref with three variants. Search hits emit a ref_text; read <ref> parses it back. The refVariant() method is unexported, so no outside package can implement the interface, which closes the sum at compile time.

// internal/model/ref.go
type Ref interface {
    refVariant()          // unexported; no outside impls
    Kind() RefKind
    Valid() bool
}
type MessageRef  struct { Session SessionKey; Entry EntryID }
type SessionRef  struct { Session SessionKey }
type ArtifactRef struct { SHA SHA256Hex }

func FormatRef(r Ref) string {
    switch r := r.(type) {
    case MessageRef:  return "msg:v1:"      + b64(r.Session.String()) + ":" + b64(r.Entry.String())
    case SessionRef:  return "session:v1:"  + b64(r.Session.String())
    case ArtifactRef: return "artifact:v1:" + r.SHA.String()
    }
    panic("unknown ref variant")
}

// internal/archive/archive.go
func ManifestStateSHA256(m model.Manifest) string {
    state := struct {
        Schema       string
        MachineID    string
        MachineLabel string
        Source       model.ManifestSource
        Policy       model.ManifestPolicy
        Adapters     []model.ManifestAdapt
        Files        []model.ManifestFile
    }{
        Schema: m.Schema, MachineID: m.MachineID, ...   // bundle_id and captured_at excluded
        Files:  m.Files,
    }
    b, _ := json.Marshal(state)
    sum := sha256.Sum256(b)
    return hex.EncodeToString(sum[:])
}

Append-only, with conflict-as-quarantine

internal/corpus/schema.go

Two snapshots of the same Pi session can disagree on a previously written line (active JSONL files, edits, replays). A naïve UPSERT loses evidence. The schema makes that impossible: triggers abort every UPDATE and DELETE on the append-only tables, and a conflict trigger quarantines duplicate entry IDs with different hashes. Try it:

entries 0 rows

    conflicts 0 rows

      ingest_attempts 0 rows

        click a button. the database state above updates immediately. red buttons exercise the append-only triggers.

        Triggers catch runtime drift. A static test under internal/testquality reads production .go files at CI time and fails the build if any of them emits UPDATE or DELETE against the append-only tables. Two independent layers, two different adversaries.

        Why not just INSERT OR REPLACE?

        The obvious shape for a re-ingest path. Two snapshots of the same session, two SQL designs, two different futures:

        Naïve silent data loss

        INSERT OR REPLACE INTO entries
       (session_key, entry_id, role, entry_sha256, ...)
VALUES (?, ?, ?, ?, ...);

        Snapshot A inserts entry-42 with hash h1. Snapshot B inserts entry-42 with hash h2 (the user edited the JSONL line before re-snapshotting). Snapshot A is silently overwritten. The disagreement leaves no evidence behind. Search results change retroactively. Two agents on two machines could even race to overwrite each other's view.

        aha append-only + quarantine

        -- attempted INSERT runs the trigger first
-- existing row stays
-- new conflicting row is dropped by RAISE(IGNORE)
-- the disagreement is RECORDED as evidence:
INSERT INTO conflicts(session_key, entry_id,
                      first_entry_sha256, second_entry_sha256,
                      details_json) ...

        The first snapshot wins. The second snapshot's row is dropped, but the disagreement is recorded in conflicts for aha conflicts to surface. Evidence is preserved without overwriting it. Two agents on two machines see the same coherent history; conflicts are explicit, not silent.

        What the trigger does, line by line

        create trigger entries_conflict_before_insert  before insert on entries  when exists(select 1 from entries              where session_key=new.session_key                and entry_id=new.entry_id) begin    insert into conflicts(session_key, entry_id,                          first_entry_sha256,                          second_entry_sha256,                          details_json)      select new.session_key, new.entry_id,             e.entry_sha256, new.entry_sha256,             json_object('kind','same-session-trigger')        from entries e       where e.session_key=new.session_key         and e.entry_id=new.entry_id         and e.entry_sha256<>new.entry_sha256;    select raise(ignore);  end;
        L2BEFORE insert Fire BEFORE the row is written. RAISE(IGNORE) later cancels the insert without aborting the surrounding transaction.
        L3-5Only on a duplicate (session_key, entry_id) WHEN exists(...) means: this trigger doesn't fire for fresh entries. First insert wins straight through.
        L14-16Only record when hashes differ e.entry_sha256 <> new.entry_sha256 filters the SELECT feeding the conflicts insert. Duplicate INSERT of the same content is recorded silently in ingest_attempts elsewhere; only true disagreement reaches conflicts.
        L17RAISE(IGNORE) – the original wins Drops the new row without raising an error. The transaction continues. The earlier insert remains the canonical truth.
        Tradeoff
        First-write wins is a deliberate choice. If snapshot A ingested on Monday and snapshot B (with edits) on Tuesday, B's edits sit in conflicts rather than overwriting A in entries. That's correct for evidence preservation, but it means the canonical aha read result reflects the older snapshot until you explicitly inspect aha conflicts.
        The actual triggers 
        create trigger entries_conflict_before_insert
  before insert on entries
  when exists(select 1 from entries
              where session_key=new.session_key and entry_id=new.entry_id) begin
    insert into conflicts(session_key, entry_id,
                          first_entry_sha256, second_entry_sha256, details_json)
      select new.session_key, new.entry_id,
             e.entry_sha256, new.entry_sha256,
             json_object('kind','same-session-trigger')
        from entries e
       where e.session_key=new.session_key and e.entry_id=new.entry_id
         and e.entry_sha256<>new.entry_sha256;
    select raise(ignore);   -- drop the new row; keep the original
  end;

create trigger entries_no_update before update on entries
  begin select raise(abort,'entries are append-only'); end;
create trigger entries_no_delete before delete on entries
  begin select raise(abort,'entries are append-only'); end;

        Trigger-maintained FTS, with one shared predicate

        internal/corpus/fts_reconcile.go

        FTS5 virtual tables are derived, but they're maintained synchronously by triggers on the source tables. Normal writes never drift. Verification compares rowid identity (cheap query plan); a public aha verify --repair-fts rebuilds from source rows when external SQL has scrambled things. 

        -- on every message insert, mirror text into FTS:
create trigger messages_ai after insert on messages
  when trim(coalesce(new.text,''))<>'' begin
    insert into fts_messages(rowid, session_key, entry_id, text)
      values(new.rowid, new.session_key, new.entry_id, new.text);
  end;

-- ftsMessageTextPredicate("")  ==  trim(coalesce(text,''))<>''
-- the SAME expression is reused in:
--   * the schema trigger above
--   * corpus.Verify        (which messages SHOULD have FTS rows?)
--   * ReconcileFTS         (which rows to re-insert)
-- verify and repair can never disagree on what counts as indexable.

        The cleanup that made this honest: until migration v7 the artifact trigger used a slightly different predicate from the verifier, so verify would flag missing FTS rows that --repair-fts wouldn't repair. The duplication-refactor pass moved both to a shared helper, and migration v7 recreates the trigger on existing corpora.

        Known-SHA handoff: trust the bytes once

        internal/archive + depot + corpus

        A naïve pipeline computes the bundle SHA three times: once when writing, once when publishing, once when ingesting. archive.WriteWithInfo threads a single WriteInfo{BundleSHA256, SizeBytes, ManifestSHA256, StateSHA256} down to depot.PutBundleKnown and corpus.IngestBundleWithExpectedSHA. The integrity boundary stays at staging, where untrusted bytes first land, but redundant rehashes go away. 

        // archive.Write computes the compressed SHA while writing.
info, _ := archive.WriteWithInfo(manifest, files, path)

// depot trusts that identity, no re-read of the finished bundle:
ref, created, _ := depot.PutBundleKnown(ctx, driver, path,
    depot.BundleRefFromWriteInfo(manifest, info, filepath.Base(path)))

// ingest verifies an expected SHA on the staged copy, not after the fact:
rep, _ := corpus.IngestBundleWithExpectedSHA(store, registry, bundlePath, info.BundleSHA256)

        Search: two FTS tables, merged in Go

        internal/search/search.go

        Messages and artifacts live in two separate FTS5 tables. A single search runs both with the same filters, each capped at the limit, then merges and re-sorts in Go by bm25 score (lower is better) with deterministic tiebreakers down to entry_id, and caps the merged result once more. The Go-side stable sort makes ranking reproducible across runs, which is verified by golden tests.

        The other half is ftsQuery. Arbitrary human text is never handed to FTS5 raw. Each whitespace-separated term is double-quoted (with embedded quotes doubled), which neutralizes FTS5 operators like AND, NEAR, *, and column filters. Type below; this widget mirrors the Go.

        FTS5 MATCH string
        terms

        Try foo AND bar, title:secret, or he said "hi". Operators get quoted into literals.

        Hand-rolled inverted index for paths

        internal/corpus/path_tokens.go

        SQLite handles the obvious data structures (B-trees, hash indexes). The interesting one in aha is the inverted index built by hand on top of SQLite so the --path-token filter has a real query plan instead of LIKE '%foo%'.

        At ingest, each session's raw_cwd is tokenized: lowercased, slash-normalized, split on /, then each segment is also split on -, _, ., and whitespace. Every distinct token becomes a row in a side table: 

        create table session_path_tokens (
  session_key text,
  token       text,
  primary key (session_key, token),
  foreign key (session_key) references sessions(session_key)
);
create index idx_session_path_tokens_token_session
  on session_path_tokens(token, session_key);

        Search then asks SQLite to use the index by name, not by hope: 

        where exists (
  select 1 from session_path_tokens spt
    indexed by idx_session_path_tokens_token_session
   where spt.token=? and spt.session_key=s.session_key
)

        The INDEXED BY hint is paired with an actual EXPLAIN QUERY PLAN test that fails CI if the plan stops using it. So the algorithmic claim ("path-token search is sublinear in sessions") is encoded as a test, not a comment. artifact_path_tokens mirrors this for artifact raw paths.

        The result is a hand-rolled inverted index inside a relational store, with an indexed-only query plan, and a test that fails if the planner stops using it. The algorithmic claim and the test that defends it live in the same package.

        Ingest

        Ingest is the only path that takes untrusted bytes into the corpus. Three roles run in order: a planner stages and validates the bundle, a writer holds an open transaction while inserting rows, and a publisher atomically renames the bundle blob into place before tx.Commit(). The commit-after-publish ordering is the contract that prevents orphans on either side of a crash.

        Stages, fully spelled out

        bundlePlanner.Prepare

        Plan

        1. stage tar.zst into a temp file
        2. compute actual SHA-256
        3. compare to expectedSHA if given
        4. read & validate manifest.json
        5. budget checks (entries, bytes, per-file)
        6. plan = { staging, sha, manifest }
        on failure: nothing in corpus changes
        corpusWriter

        Write (one tx)

        1. recordBundleAttempt; duplicate ⇒ skip + commit
        2. PrepareStatements (transaction-scoped)
        3. InsertMachineAndSources
        4. StreamManifestFiles, per-session prefetch
        5. insert entries, messages, artifacts, images
        6. triggers mirror FTS, quarantine conflicts
        tx held open; not yet committed
        blobPublisher.PromoteBundle

        Publish, then commit

        1. atomic rename staging → blobs/bundles/<sha>.tar.zst
        2. tx.Commit()
        on success: bundle & rows become visible together
        on commit-fail: promoted blob removed; no orphans

        Failure-injection hooks (test only)

        afterManifestFilessimulate a crash between writes and promote
        afterBundlePromoteBeforeCommitsimulate a crash after blob promote but before commit

        Tests assert: corpus rows roll back, the promoted blob is removed, no orphans, ingest_attempts records the duplicate. On SQLITE_BUSY the ingestor retries up to 20 times with a pluggable clock.Sleeper / clock.Backoff, so contention tests are deterministic.

        Read-visibility invariant

        corpus.IngestVisibility test

        A reader on another connection must not see uncommitted ingest rows. The paired property test holds a writer at afterManifestFiles, then a separate reader calls search.Query and corpus.ReadContext. Both see zero rows until commit, then full rows after. This is the contract that makes search-then-read coherent for agents.

        Deduplication

        Three different keys catch three different kinds of duplication, and the layers compose. Two additional set-shaped tricks below short-circuit work that would otherwise look like duplication but cost a fetch. Rows are ordered by where duplicate work is stopped; hover only adds the operational detail.

        MechanismKeyWhereEffectScope
        1 Bundle object bundle_sha256 depot bundles/v1/<sha>.tar.zst identical bytes share one object cross-machine
        2 Corpus bundle row bundle_sha256 UNIQUE corpus bundles, ingest_attempts duplicate ingest is recorded, not done per corpus
        3 File blob file_sha256 corpus blobs/<sha> raw bytes reused across bundles per corpus
        4 State equivalence state_sha256 catalog refs unchanged source reuses a ref without fetch per machine
        5 Pending set catalog − corpus aha ingest (no args) fetches only new refs; scales by new bundles, not catalog size per ingest
        Static read: duplicate work is rejected first by bundle SHA, then corpus bundle row, then file blob SHA; state and pending sets avoid unnecessary fetches. Hover a row for the operational detail.

        1. cmd/aha/main.go · 11 lines. It just calls cli.Run.
        2. internal/model/ref.go and identity.go · the sealed types every other package consumes.
        3. internal/archive/archive.go · capture, manifest, tar.zst, plus the state signature.
        4. internal/depot/depot.go + local.go / r2.go · bundle store, catalog merge.
        5. internal/corpus/schema.go · the most opinionated 270 lines: triggers do the heavy lifting.
        6. internal/corpus/ingest.go · planner, writer, publisher.
        7. internal/search/search.go · FTS5 query construction. Tiny on purpose.
        8. internal/cli/*.go · thin orchestration over the above; flag specs are shared metadata.
